## 1. Project identity

**Working name:** GB-Sec

**Core idea:** Build a handheld games console from basic embedded components, learn the hardware and firmware stack deeply, and then evolve the same platform into a rigorous embedded/hardware cybersecurity laboratory.

The project should begin simple enough to understand every subsystem and then grow deliberately. The final objective is not merely "a homemade games console". The stronger end-state is:

> **A custom handheld games console that doubles as an intentionally attackable and hardenable embedded-security platform.**

That means the project should eventually support both normal console/game-development functions and controlled security experiments against hardware and firmware that we own and designed ourselves.

## 2. Why this project exists

The project began from repairing an original Game Boy Advance AGB-001. The GBA's intermittent power behaviour strongly suggested a dirty/oxidised power switch, and repeatedly exercising the switch temporarily restored operation.

That repair experience raised a broader question: could a small handheld be designed and programmed from scratch?

The project is deliberately structured to turn that curiosity into a long-running learning platform.

Primary learning areas include embedded C/C++, microcontrollers, digital electronics, GPIO, SPI, UART, I2C, PWM, DMA, interrupts, timers, memory layout, displays, graphics, game loops, bootloaders, firmware formats, flash storage, debugging, SWD/JTAG-style interfaces, firmware analysis, secure boot, digital signatures, device authentication, threat modelling, physical attack surfaces, logic analysis, custom PCB design, and secure/insecure design comparisons.

The project should also become a portfolio piece that can be discussed with employers. The repository, documentation, commit history, diagrams, test results, security analysis, and final website article should all tell the same engineering story.

## 3. Guiding principle

A core rule for the project is:

> **Do not put important code into GB-Sec that cannot be explained.**

Libraries are acceptable and often desirable, but for the concepts central to the learning goals we should understand what is happening underneath the abstraction, especially GPIO, SPI, memory, framebuffer design, game-loop timing, the build pipeline, the boot process, firmware image formats, debug interfaces, authentication, secure boot, key storage, and security boundaries.

The project should prefer small, understandable increments over large copied examples.

## 5. Why Raspberry Pi Pico 2 W / RP2350

The Pico 2 W was chosen because it combines low cost, strong documentation, breadboard friendliness, C/C++ SDK support, enough RAM and performance for a small console, direct access to microcontroller peripherals, wireless capability for later experiments, and RP2350 security features worth exploring later.

The wireless version was preferred because Wi-Fi and Bluetooth/BLE create future directions such as networked games, wireless controllers, OTA firmware updates, secure update design, network-facing services, BLE protocol experiments, intentionally vulnerable network services, and wireless CTF-style challenges.

Wireless does not need to be used in the first prototype.

## 6. Why pre-soldered headers

The Pico 2 W was ordered with headers because the first stage is breadboard development. This avoids unnecessary early failure modes such as poor solder joints, misaligned headers, accidental bridges, and mechanical issues.

Soldering will become part of the project later when the custom PCB stage begins.

## 7. Why the separate ST7789 module

The separate Waveshare ST7789 module was preferred over a Pico-specific display pack because the project is intended to teach the actual wiring and interface.

Benefits include explicit SPI wiring, explicit GPIO allocation, easier migration to a custom PCB, freedom to choose the physical console layout later, and better visibility into chip-select, clock, data, reset, data/command, and backlight behaviour.

Typical display pins:

- VCC
- GND
- DIN / MOSI
- CLK / SCK
- CS
- DC
- RST
- BL

The display generally does not require MISO for basic write-only graphics.

## 9. Button electrical model

The first button circuit should be:

```text
GPIO ---- button ---- GND
```

The RP2350 internal pull-up resistor can be enabled.

This produces active-low behaviour:

- released -> HIGH
- pressed -> LOW

This avoids needing external pull-up resistors and is a common embedded pattern.

Many four-legged tactile switches contain two internally connected pairs of legs, so breadboard orientation matters.

## 10. Development platform

Primary environment:

- Windows 11

- Git / GitHub

WSL2 should remain available as a secondary environment for Linux tooling, Python scripts, firmware-analysis utilities, binary inspection, security tooling, and scripting.

## 11. Why C/C++ instead of MicroPython

C/C++ was chosen because the learning objectives include memory layout, compilation, linking, firmware images, low-level peripheral access, interrupts, timing, DMA, boot processes, and embedded security.

The project should use the Pico SDK rather than abstracting away most of the system.

This does not mean every subsystem must be written from scratch. It means important behaviour should be understood.

## 12. Build pipeline mental model

This is a cross-compilation project.

```text
C source code
    |
    v
preprocessor / compiler
    |
    v
target object files
    |
    v
linker
    |
    +--> ELF executable
    +--> BIN image
    +--> HEX image
    +--> UF2 image
```

Important distinction:

- CMake configures the build
- the compiler translates C/C++ into target machine code
- the linker combines object files and libraries
- the Pico SDK provides platform support and Pico-specific build logic
- a build tool such as Ninja executes the generated build graph

## 13. Current CMake structure

The firmware `CMakeLists.txt` currently:

1. requires a minimum CMake version
2. selects `pico2_w` as the board
3. imports the Pico SDK helper
4. declares the `gb_sec` project
5. selects C11 / C++17
6. initialises the Pico SDK
7. creates the `gb_sec` executable target
8. adds `src/main.c`
9. links against `pico_stdlib`
10. enables USB stdio
11. disables UART stdio for now
12. enables compiler warnings
13. generates extra outputs such as UF2/BIN/HEX

The current firmware entry point is intentionally minimal because the first goal is to prove the toolchain can produce a valid firmware image.

## 14. pico_sdk_import.cmake purpose

The `pico_sdk_import.cmake` helper answers:

> Where is the Raspberry Pi Pico SDK and how should CMake load it?

Its responsibilities include reading `PICO_SDK_PATH`, reading relevant environment variables, optionally fetching the SDK from Git, validating the SDK directory, locating `pico_sdk_init.cmake`, and importing the SDK CMake entry point.

The project-specific `CMakeLists.txt` describes GB-Sec.

The SDK import file describes how to make the Pico SDK available.

A future cleanup should replace the simplified helper in this repo with the exact upstream helper supplied by the Pico SDK/template rather than maintaining a custom approximation.

## 16. Debugging philosophy

Failures should be preserved when they teach something.

A useful debugging entry should contain observed behaviour, expected behaviour, initial hypotheses, tests performed, evidence, root cause, fix, and lesson.

Example:

```text
Problem:
Display showed random pixels.

Hypothesis:
SPI clock too fast.

Test:
Reduced clock frequency.

Result:
No change.

Further test:
Captured CS/DC/SCLK/MOSI with logic analyser.

Finding:
DC changed after transfer began.

Root cause:
Incorrect ordering in display_write_command().

Fix:
Set DC before asserting CS and sending bytes.

Lesson:
Protocol understanding was more useful than guessing at timing.
```

## 19. Phase progression

### Phase 0 — environment and repository
Goal: reproducible build environment, Pico 2 W target, minimal firmware, documentation baseline, clean Git structure.

Learning: CMake, SDK import, toolchain, cross-compilation, ELF/UF2/BIN formats, repository hygiene.

### Phase 1 — GPIO and controls
Wire one button, configure GPIO input, enable pull-up, detect active-low press, expand to eight buttons.

Learning: GPIO modes, pull resistors, active-high vs active-low, switch internals, debouncing, digital logic levels.

### Phase 2 — display bring-up
Connect ST7789 over SPI, initialise display, fill screen with a solid colour, draw a pixel, draw a rectangle.

Learning: SPI, MOSI, SCLK, CS, DC, RESET, command/data distinction, pixel formats, RGB565, transfer timing.

### Phase 3 — framebuffer and graphics
For 320 x 240 RGB565:

```text
320 * 240 * 2 bytes
= 153,600 bytes
~= 150 KB
```

Engineering questions include direct drawing vs framebuffer, single vs double buffering, partial updates, DMA transfers, memory pressure, sprite storage, and tile maps.

### Phase 4 — game loop
Implement simple Pong and separate input, update, and render.

```text
while (running)
    input_update()
    game_update()
    game_render()
    display_present()
```

Learning: frame timing, deterministic updates, input state, game state, rendering, engine architecture.

### Phase 5 — audio
Later add PWM or I2S audio, a small amplifier, and speaker.

Potential hardware: MAX98357A or equivalent.

### Phase 6 — removable storage
Add microSD, likely over SPI initially.

Learning: shared buses, chip-select, filesystems, block storage, parsing, error handling.

### Phase 7 — game launcher
Add game list, metadata, loader, simple menu, and persistent settings.

This marks the transition from "firmware containing a game" to "console platform".

## 21. Why a VM / bytecode is attractive

Games should eventually not need to be native RP2350 firmware blobs.

A small custom VM or bytecode format could provide a stable game ABI, safer execution, easier validation, simpler portability, a clear security boundary, and an educational runtime/CPU project.

Possible VM concepts:

- instruction decoding
- registers
- memory model
- host functions / syscalls
- graphics API
- input API
- audio API
- sandboxing

A custom bytecode also creates useful cybersecurity exercises around malformed programs, loader bugs, parser bugs, bounds checking, capability design, and isolation.

## 22. Security progression

The security side should be introduced experimentally.

Do not begin with "secure boot" as an isolated checkbox.

Build insecure versions first, demonstrate the failure, then harden.

That progression is central to the learning value.

## 23. Integrity vs authenticity

A future loader could initially check SHA-256.

If an attacker can alter both payload and stored hash, they can modify the game, compute a new hash, replace the stored hash, and pass validation.

Therefore:

> A matching hash does not prove who created the software.

This gives a natural reason to move from hashing to digital signatures.

## 24. Signed games

A stronger loader might:

```text
Read game
   ->
validate header
   ->
hash payload
   ->
verify digital signature
   ->
run only if valid
```

The console stores a public verification key. The signing private key remains off-device.

This demonstrates software authenticity.

## 25. Cartridge/device authentication

A second microcontroller could act like a cartridge or secure peripheral.

### Bad version
```text
Console -> cartridge: "Are you genuine?"
Cartridge -> console: "YES"
```

### Slightly better but weak
Static password.

### Better
Challenge-response.

### More mature
A cryptographic protocol with nonce/challenge, authenticated response, replay resistance, and key-management strategy.

Each version can be attacked and documented.

## 26. Security MCU / second-device idea

Future architecture:

```text
Main RP2350
    |
    | UART / SPI / I2C
    v
Security / cartridge MCU
```

The secondary device could hold keys, authentication state, challenge-response logic, secure counters, or protected secrets.

The educational goal is to make trust boundaries and protocol failures observable.

### Important caution

## 32. Threat-modelling approach

Every security control should state:

1. what asset is being protected
2. who the attacker is
3. what capability the attacker has
4. what attack is being prevented
5. what assumptions remain
6. what the mitigation does not protect against

Example:

### Feature
Game authentication.

### Asset
Ability to control which game code is accepted.

### Attacker capability
Can modify files on removable storage.

### Weak design
Hash stored beside payload.

### Attack
Modify payload and replace hash.

### Root cause
Hash provides integrity checking but no proof of origin.

### Hardened design
Developer signs manifest/payload.

### Console stores
Public verification key only.

### Remaining limitation
A physical attacker may still target keys, boot configuration, runtime memory, or debug interfaces depending on the architecture.

## 42. Display concepts to understand

When ST7789 work begins, understand:

- SPI is synchronous
- clock is generated by the controller/master
- MOSI carries controller-to-display data
- MISO may be unused
- CS selects the device
- DC distinguishes command bytes from display-data bytes
- reset defines controller startup state
- pixel format determines bytes per pixel
- orientation may be controlled by controller registers
- transfer bandwidth affects frame rate

Later use a logic analyser to correlate code with actual wire behaviour.

## 43. Framebuffer / DMA progression

6. measure frame times
7. consider dirty rectangles / partial updates

Each optimisation should be motivated by measured limitations.
